# DDR-002: the D1 insert statement, written by GitHub Copilot (HW4)

Written retroactively on 2026-09-29 for a delegation made on 2026-09-22. HW4's
AI Use section described it in prose; this records it properly. The verification
below was performed at the time, not reconstructed.

## Task

Write the `INSERT` statement in `worker.js` that stores a validated contact entry
into the D1 `entries` table: `body.coachName`, `body.school`, `body.contactDate`,
and `body.status` into the columns `coach_name`, `school`, `contact_date`, and
`status`.

Deliberately scoped to that one statement. The route, the CORS handling, the
validation that traces to `FEATURES.md` E12, and the `SELECT` with its column
aliases were all written before Copilot was asked, and the insert was left as a
marked `TODO` so the delegation would be a single identifiable thing rather than
a vague contribution.

## Tool and model

**GitHub Copilot**, Copilot Chat, agent mode, in a GitHub Codespace on the HW4
repository, 2026-09-22. Free plan. **The model was not recorded at the time and
cannot now be recovered** — Copilot Chat did not display it prominently and I did
not think to check. That is a gap in this record and the reason "check the model
before you start" is now an entry in `SKILLS.md`.

## Economic rationale

| | Hours (mine) |
|---|---|
| Build by hand, at my HW4 pace | ~0.25 |
| Tool run | ~0.05 |
| Review and fixes | ~0.35 |
| **Net** | **−0.15, a loss** |

**Was it worth it?** By the clock, no. Verifying eight lines of SQL took longer
than writing them would have, and this is the honest number rather than a
flattering one.

Two things complicate that verdict without overturning it. Verification is
roughly fixed-cost regardless of who wrote the code, so the loss is really the
cost of *checking*, which I would owe on my own work too and usually skip. And
the check produced the SQL-injection test that is still in the repository and
still runs. **The rule this gives me: delegating a task smaller than its own
verification cost is a losing trade on time**, and the reason to do it anyway is
to learn what checking that kind of output requires.

answer, sent to GitHub's model as prompt material. That included `worker.js`,
`schema.sql`, and whatever else was in context. The repository was already public,
so this added no exposure it did not already have — **which is a fact about the
repository, not a safety property of the tool.** If this repository were ever made
private, the same delegation would become a real crossing and `TOOLS.md` would

**Reverse crossing: nothing.** Copilot returned eight lines of JavaScript, no
dependency, no package, no configuration, no hidden instruction file. Compared
with DDR-001, where the tool returned nineteen dependencies and a competing
prompt, this is the sharpest contrast in the two records: a chat assistant editing
inside my repository brought nothing back in, and a hosted app builder brought
back an entire stack.

## Verification performed

- **Read the shape.** Confirmed the SQL used `?` placeholders with the values in
  a separate `.bind(...)`, rather than concatenating user input into the
  statement. This is the one check I could perform by reading, and it is the
  check `STANDARDS.md` rule 8 exists to demand.
- **Tested the column mapping by hand.** `POST` of four deliberately distinct
  values — `AAA-COACH`, `BBB-SCHOOL`, `2026-01-02`, `CCC-STATUS` — then read them
  back from `GET /entries` to confirm each landed in its own field.
- **Tested the claim `bind()` actually makes.** Saved a coach named
  `Robert'); DROP TABLE entries;--` and confirmed it came back as an ordinary
  name with the table intact and the other rows untouched.
- Both are recorded as rows in HW4's `FEATURES.md` verification table.

## Findings

**Rows passing: 1 of 1.** Copilot produced the parameterised version, not the
concatenated one the assignment predicted it would offer.

**Failures and what I changed:** none in the code. One change to my own
expectations: the assignment warned that Copilot would hand me concatenated SQL
and it did not. My reading is that the four queries already in that file used
`prepare().bind()`, so it matched its neighbours. **The safety came from the
context it sat in, not from the tool being reliably careful**, and I did not test
whether it would answer the same way in an empty file.

**Could not fully verify, and what I did about it:** I could check the *shape* of
the SQL by reading it. I could not check by reading that the four bound values
line up with the four columns in the right order — `coach_name, school,
contact_date, status` against `coachName, school, contactDate, status`. A swapped
pair would run without error, return `201`, and store the school in the coach
field permanently. Reading it more carefully would not have caught that.
**What I did:** tested it with four visibly different values and read them back,
which is the only check that could have found a swap.
